Unlike a fixed hub-and-spoke coverage tool, this framework spans the whole front-end lifecycle — the orchestrator's 12 stages are mostly sequential and gated, not fanned out. There is one verification environment (standard SystemVerilog UVM, run on Vivado xsim); the genuine parallel fork is the two independent review agents, each running in fresh context with no stake in the changes it's checking.

05a

How a Cycle Gets Checked

Standard SystemVerilog UVM on xsim — the components, and how they combine to check the DUT every clock.

This is a conventional UVM environment: a reusable protocol UVC, a layered env with RAL and a reference-model scoreboard, functional coverage sampled by the monitor, and a bound SVA layer — all compiled, elaborated, and run on Vivado xsim with its built-in UVM 1.2 (-L uvm). Native rand/constraint/dist drive the stimulus; -sv_seed makes each seed reproducible.

The components

UVM componentRoleWhere
Driver / SequencerReusable APB UVC drives the bus from constrained-random seq_items; the RAL runs through its reg adaptervip/apb/sv/
MonitorSamples the APB transactions and DUT outputs, publishes them on an analysis port every transferapb_monitor.sv
Reference-model scoreboardPredicts register readback + protocol (PSLVERR, wait states) and checks the DUT against itpmtpc4_scoreboard.sv
Functional covergroupsRegister/config + white-box FSM covergroups, sampled by the monitor/scoreboard from a signal it just checkedpmtpc4_coverage.sv / sva/
Code coverage (stmt/branch/cond/toggle)xsim's own RTL instrumentation via xelab -cc_type sbct, merged across seeds with xcrgxelab --cov
SVA protocol assertionsBound white-box modules asserting APB handshake, PWM waveform, IRQ aggregation, freeze, resetdv/sv/sva/*.sv
RALPeakRDL-generated uvm_reg_block wired via the adapter + an explicit predictor (auto-predict off)pmtpc4_ral_pkg.sv

Step by step: how a single cycle gets checked

  1. A UVM sequence randomizes a seq_item (native rand/constraint) and sends it to the driver — e.g. a write to CH0_COMPARE.
  2. The driver drives the APB bus; the monitor samples the transaction and DUT outputs (prdata, pready, pslverr, pwm_out, irq, INT_STATUS) and publishes them.
  3. The scoreboard/RAL predictor independently computes what those signals should be from the spec/RAL model — not from the RTL — and compares, signal by signal.
  4. The bound SVA layer checks cycle-accurate relationships continuously (handshake timing, waveform rule, freeze, valid-state) in parallel with the transaction checks.
  5. Coverage is sampled only from a signal that was just checked — by the monitor/scoreboard, never by a test calling .sample(). Coverage is a side effect of a passing check, not an independent claim.
  6. run_regression.py repeats this across every test × N seeds (-sv_seed), collecting functional + code coverage per run.
  7. coverage-closure merges the databases with xcrg, triages every unhit bin (add stimulus, waive with a structural reason, or file as a bug), and loops to the goal.
  8. verification-reviewer then deliberately seeds a bug (e.g. a flipped comparison), reruns, and confirms the checks actually fail — proof the scoreboard/SVA isn't decorative — then reverts.
xsim gotcha, from the real bring-up: a white-box channel assertion fired every clock even though state_o was correct — xsim samples the preponed value of a continuous-assign net (assign state_o = state;) as X. The fix is to bind the SVA to the registered state reg, not its combinational alias. This class of simulator-specific lesson is exactly what a real UVM sim surfaces and a generated-but-never-run env hides.

Stage 8-9 — Test Authoring

Agent: test-writer · The single most important rule in the whole pipeline lives here.

flowchart LR
    A["vplan.yaml + envs"]:::disk --> B["test-writer"]:::exec
    B --> C["directed + constrained-random tests\ncovergroups wired to vPlan IDs"]:::disk
    C --> D{{"does a TEST call\nthe coverage API directly?"}}:::decision
    D -->|yes| E["FORBIDDEN\nredirect: fix why the monitor\nisn't observing the scenario"]:::fail
    D -->|no - monitor samples it| F["RAL / register verification\nmilestone"]:::exec
    F --> G["Functional tests"]:::disk

    classDef exec fill:#1F6F5C,stroke:#0E4A3C,color:#ffffff;
    classDef decision fill:#E3E8ED,stroke:#3B5166,color:#131A19,font-weight:600;
    classDef fail fill:#B5502E,stroke:#7A3720,color:#ffffff;
    classDef disk fill:#ffffff,stroke:#6C7672,color:#131A19;
  • test-writer.md Coverage may only be sampled by the monitor/scoreboard, from a signal it just checked — never by test/sequence code calling .sample() directly. A test's job is to create a scenario, never to declare it covered.
  • test-writer.md Every test maps to ≥1 vPlan ID; self-checking against the scoreboard/RAL, never eyeballing waveforms.
Hard-won rule: an environment can reach "100%" functional coverage while checking almost nothing — if tests call the coverage API directly to mark bins covered, disconnected from any signal actually observed. Coverage must be sampled only by the monitor/scoreboard, from a signal it just checked. This is why test-writer.md states the rule explicitly instead of leaving it implied — the single most important discipline in the pipeline.

  • coverage-triage Classify every hole: reachable → stimulus, unreachable → justified waiver, bug → file back with evidence. Never silently drop one.
  • coverage-closure.md "100% functional coverage with failing/absent checks is not closure" — pass/fail and coverage must both be green, and the scoreboard must actually be checking.
  • verification-review skill Waivers matched by rule/pattern, never a hand-maintained allow-list of point names — a pattern keeps catching new holes; a name list silently stops.
On PMTPC-4: the loop runs on xsim via run_regression.py (every test × N seeds) with xcrg-merged functional + code coverage. Four real RTL design bugs were found and fixed while verifying this IP (PREADY timing, skipped LOAD state, missing SOFT_RESET clear, live-vs-shadow COMPARE) — closure is about finding those, not just filling bins. xsim does not report assertion coverage, so assertion evidence rolls up as pass/fail plus SVA cover.

Stage 11 — Independent Review

Agents: design-reviewer, verification-reviewer · Fresh context, no stake in the changes just made.

flowchart TD
    A["Closure output\n(RTL + reports/coverage_summary.md)"]:::disk --> B["design-reviewer"]:::exec
    A --> C["verification-reviewer"]:::exec
    B --> D["re-derive expected behavior\nfrom spec, cold - compare to RTL"]:::exec
    C --> E["checker vacuity check +\nMUTATION SPOT-CHECK:\nseed bug -> rerun -> confirm FAIL -> revert"]:::exec
    D --> F{{"any CONFIRMED finding?"}}:::decision
    E --> F
    F -->|yes| G["back to owning agent\nwith exact evidence"]:::fail
    F -->|no| H["Signoff-ready"]:::pass

    classDef exec fill:#1F6F5C,stroke:#0E4A3C,color:#ffffff;
    classDef decision fill:#E3E8ED,stroke:#3B5166,color:#131A19,font-weight:600;
    classDef fail fill:#B5502E,stroke:#7A3720,color:#ffffff;

  • design-review skill Rebuild the contract from the spec before reading the RTL — an inline comment's justification is a claim, never proof.
  • verification-review skill Mutation/bug-seeding is the standard way to prove a checker works: seed an obviously-wrong change, confirm something fails, always revert immediately — never leave a seeded bug in the tree.
  • both skills Report, don't fix. Reviewing and fixing in the same pass re-introduces the confirmation bias the review exists to avoid.
Real example — PMTPC-4: the verification-reviewer seeded two deliberate bugs — a comparison operator flip in the PWM channel core, and a removed write-gate in the APB error decode — in two different modules. Both were caught immediately by the existing checks (one via 6 reference-model errors, the other at three independent layers simultaneously). Both were reverted and confirmed clean via git diff before the full suite was re-run green.
