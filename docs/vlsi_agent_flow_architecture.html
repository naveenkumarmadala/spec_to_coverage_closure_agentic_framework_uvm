The design thread and verification thread run independently from the moment requirements.md/design_spec.md exist — vPlan authoring only needs the register map, and env authoring (RAL, scoreboard skeleton, coverage model, SVA) doesn't need working RTL, only RTL's interface. The two threads share nothing else until the simulation gate, where verification's stimulus runs against design's RTL for the first time. Each thread carries its own independent review agent, scoped to its own artifacts and explicitly forbidden from reading the other thread's collateral — design-reviewer never opens dv/, verification-reviewer re-derives expected checker behavior from spec before ever comparing it to the RTL, and neither reads the other's report before finishing its own.

  • lint-static-checker.md One command, flow/scripts/static_gate.py: Verible lint, xsim elaboration of the DUT alone, Vivado out-of-context synthesis. Deny-by-default — any unclassified warning fails; per-IP waivers need a written reason.

Real example — PMTPC-4: four RTL bugs shipped past the static gate before being caught: a protocol phase decoded from a registered instead of combinational state (PREADY one cycle late on every transfer), a skipped FSM state on periodic reload, a missing hardware-clear on SOFT_RESET, and a mid-RUNNING COMPARE write applying live instead of shadowed. The design review also cross-referenced the Register Spec against the Design Spec's own FSM table and confirmed a fifth, initially-suspected gap (CH_EN=0 during LOAD/EXPIRED) was actually already correct — the Register Spec's field description said "regardless of current state," which the Design Spec's transition table alone didn't state.

05a

How a Cycle Gets Checked

Standard SystemVerilog UVM on xsim — the components, and how they combine to check the DUT every clock.

This is a conventional UVM environment: a reusable protocol UVC, a layered env with RAL and a reference-model scoreboard, functional coverage sampled by the monitor, and a bound SVA layer — all compiled, elaborated, and run on Vivado xsim with its built-in UVM 1.2 (-L uvm). Native rand/constraint/dist drive the stimulus; -sv_seed makes each seed reproducible.

The components

UVM componentRoleWhere
Driver / SequencerReusable APB UVC drives the bus from constrained-random seq_items; the RAL runs through its reg adaptervip/apb/sv/
MonitorSamples the APB transactions and DUT outputs, publishes them on an analysis port every transferapb_monitor.sv
Reference-model scoreboardPredicts register readback + protocol (PSLVERR, wait states) and checks the DUT against itpmtpc4_scoreboard.sv
Functional covergroupsRegister/config + white-box FSM covergroups, sampled by the monitor/scoreboard from a signal it just checkedpmtpc4_coverage.sv / sva/
Code coverage (stmt/branch/cond/toggle)xsim's own RTL instrumentation via xelab -cc_type sbct, merged across seeds with xcrgxelab --cov
SVA protocol assertionsBound white-box modules asserting APB handshake, PWM waveform, IRQ aggregation, freeze, resetdv/sv/sva/*.sv
RALPeakRDL-generated uvm_reg_block wired via the adapter + an explicit predictor (auto-predict off)pmtpc4_ral_pkg.sv

Step by step: how a single cycle gets checked

  1. A UVM sequence randomizes a seq_item (native rand/constraint) and sends it to the driver — e.g. a write to CH0_COMPARE.
  2. The driver drives the APB bus; the monitor samples the transaction and DUT outputs (prdata, pready, pslverr, pwm_out, irq, INT_STATUS) and publishes them.
  3. The scoreboard/RAL predictor independently computes what those signals should be from the spec/RAL model — not from the RTL — and compares, signal by signal.
  4. The bound SVA layer checks cycle-accurate relationships continuously (handshake timing, waveform rule, freeze, valid-state) in parallel with the transaction checks.
  5. Coverage is sampled only from a signal that was just checked — by the monitor/scoreboard, never by a test calling .sample(). Coverage is a side effect of a passing check, not an independent claim.
  6. run_regression.py repeats this across every test × N seeds (-sv_seed), collecting functional + code coverage per run.
  7. coverage-closure merges the databases with xcrg, triages every unhit bin (add stimulus, waive with a structural reason, or file as a bug), and loops to the goal.
  8. verification-reviewer then deliberately seeds a bug (e.g. a flipped comparison), reruns, and confirms the checks actually fail — proof the scoreboard/SVA isn't decorative — then reverts.
xsim gotcha, from the real bring-up: a white-box channel assertion fired every clock even though state_o was correct — xsim samples the preponed value of a continuous-assign net (assign state_o = state;) as X. The fix is to bind the SVA to the registered state reg, not its combinational alias. This class of simulator-specific lesson is exactly what a real UVM sim surfaces and a generated-but-never-run env hides.

Stage 8-9 — Test Authoring

Agent: test-writer · The single most important rule in the whole pipeline lives here.

flowchart LR
    A["vplan.yaml + envs"]:::disk --> B["test-writer"]:::exec
    B --> C["directed + constrained-random tests\ncovergroups wired to vPlan IDs"]:::disk
    C --> D{{"does a TEST call\nthe coverage API directly?"}}:::decision
    D -->|yes| E["FORBIDDEN\nredirect: fix why the monitor\nisn't observing the scenario"]:::fail
    D -->|no - monitor samples it| F["RAL / register verification\nmilestone"]:::exec
    F --> G["Functional tests"]:::disk

    classDef exec fill:#1F6F5C,stroke:#0E4A3C,color:#ffffff;
    classDef decision fill:#E3E8ED,stroke:#3B5166,color:#131A19,font-weight:600;
    classDef fail fill:#B5502E,stroke:#7A3720,color:#ffffff;
    classDef disk fill:#ffffff,stroke:#6C7672,color:#131A19;
  • test-writer.md Coverage may only be sampled by the monitor/scoreboard, from a signal it just checked — never by test/sequence code calling .sample() directly. A test's job is to create a scenario, never to declare it covered.
  • test-writer.md Every test maps to ≥1 vPlan ID; self-checking against the scoreboard/RAL, never eyeballing waveforms.
Hard-won rule: an environment can reach "100%" functional coverage while checking almost nothing — if tests call the coverage API directly to mark bins covered, disconnected from any signal actually observed. Coverage must be sampled only by the monitor/scoreboard, from a signal it just checked. This is why test-writer.md states the rule explicitly instead of leaving it implied — the single most important discipline in the pipeline.

  • coverage-closure.md "100% functional coverage with failing/absent checks is not closure" — pass/fail and coverage must both be green, and the scoreboard must actually be checking.

On PMTPC-4: the loop runs on xsim via run_regression.py (every test × N seeds) with xcrg-merged functional + code coverage. Four real RTL design bugs were found and fixed while verifying this IP (PREADY timing, skipped LOAD state, missing SOFT_RESET clear, live-vs-shadow COMPARE) — closure is about finding those, not just filling bins. xsim does not report assertion coverage, so assertion evidence rolls up as pass/fail plus SVA cover.

Independent Review — One Per Thread, Keyed to Its Own Changes

Agents: design-reviewer (design thread, stage 5.5), verification-reviewer (verification thread, stage 11) · Fresh context each run, no stake in the changes just made, and neither reads the other's report first.

flowchart TD
    RTLCH["RTL/RDL changed\n(design thread, or coverage-closure\nediting RTL during triage)"]:::disk --> DR["design-reviewer\nre-derive expected behavior\nfrom spec, cold - never reads dv/"]:::exec
    DVCH["DV collateral changed\n(verification thread, or closure\nadding a test/checker)"]:::disk --> VR["verification-reviewer\nre-derive expected CHECKER behavior\nfrom spec first, THEN compare to DV code +\nMUTATION SPOT-CHECK: seed bug -> rerun -> confirm FAIL -> revert"]:::exec

    DR --> F1{{"CONFIRMED finding?"}}:::decision
    VR --> F2{{"CONFIRMED finding?"}}:::decision
    F1 -->|yes| G1["back to rtl-designer\nwith exact evidence"]:::fail
    F2 -->|yes| G2["back to tb-architect/test-writer\nwith exact evidence"]:::fail
    F1 -->|no| H1["Design thread signoff-ready"]:::pass
    F2 -->|no| H2["Verification thread signoff-ready"]:::pass
    G1 -.re-run scoped to fix.-> DR
    G2 -.re-run scoped to fix.-> VR

  • design-reviewer.md Never reads ips/<ip>/dv/ — independence from the verification thread is a stated rule, not an informal convention. Rebuild the contract from the spec before reading the RTL; an inline comment's justification is a claim, never proof.
  • verification-reviewer.md Reads requirements.md/design_spec.md as a primary input, on equal footing with the DV collateral — independently re-derives what a checker should check before looking at what it actually does, the same discipline design-reviewer applies to RTL. A checker comment that cites RTL behavior instead of a spec clause is itself a finding.
  • verification-review skill Mutation/bug-seeding is the standard way to prove a checker works: seed an obviously-wrong change, confirm something fails, always revert immediately — never leave a seeded bug in the tree.
  • both agents Report, don't fix, and don't read each other's findings before finishing your own — reviewing-and-fixing in the same pass, or anchoring on the other reviewer's conclusion, both re-introduce the confirmation bias independent review exists to avoid.
Real example — PMTPC-4: the verification-reviewer seeded two deliberate bugs — a comparison operator flip in the PWM channel core, and a removed write-gate in the APB error decode — in two different modules. Both were caught immediately by the existing checks (one via 6 reference-model errors, the other at three independent layers simultaneously). Both were reverted and confirmed clean via git diff before the full suite was re-run green. In a later pass, design-reviewer and verification-reviewer were dispatched at the same time against the same open question (a PWM-gating formula that looked narrower in the spec than in the RTL) — neither was shown the other's conclusion, and both independently recommended widening the spec to match the RTL rather than narrowing the RTL, for the same underlying reason (the spec's own stated requirement carried no state qualifier). Two independently-reached conclusions agreeing is real corroborating evidence in a way one reviewer's opinion never is.

Lessons Learned

Nine discoveries from PMTPC-4's first run through the pipeline, plus a second, deeper audit pass (design thread and verification thread run as fully independent, mutually-blind reviews — see Section 8) that found five more real bugs and three durable methodology lessons. Full evidence for the second pass lives in ips/pmtpc4/reports/coverage_waivers.md; this table is the condensed, permanent-change version.

#DiscoveryImpactChange made

5First-generation coverage model sampled bins directly from test code"100%" coverage that checked almost nothingRebuilt around a cycle-accurate reference model; anti-pattern rule added to test-writer.md
6peakrdl-regblock's field_combo struct trips Verilator MULTIDRIVEN on every IPWould be rediscovered per-IPShared, filename-matched flow/tools/verilator_waivers.vlt
